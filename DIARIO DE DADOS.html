Crie o DIAGRAMA ENTIDADE-RELACIONAMENTO (DER) do projeto: "Entrega 1 — Modelo Conceitual (DER) Barbearia The Family Hair" O DER deve ser construído EXCLUSIVAMENTE com base na estrutura conceitual definida neste README. IMPORTANTE: Não utilizar como base a estrutura antiga da imagem original da barbearia. Não criar entidades, atributos ou relacionamentos que não estejam definidos na estrutura final deste README. O objetivo é representar visualmente o modelo conceitual do sistema de gerenciamento da barbearia. ================================================== ENTIDADES FINAIS ================================================== O DER deve possuir EXATAMENTE estas 7 entidades: 1. CLIENTE 2. PROFISSIONAL 3. SERVICO 4. AGENDAMENTO 5. ITEM_AGENDAMENTO 6. PAGAMENTO 7. AVALIACAO NÃO criar: - AGENDAMENTO_SERVICO - TABLE - MESA - ESTACAO - outras entidades não especificadas. A entidade associativa deve se chamar exatamente: ITEM_AGENDAMENTO ================================================== 1. CLIENTE ================================================== Atributos: ID_CLIENTE — PK NM_CLIENTE CD_TELEFONE CD_EMAIL DT_CADASTRO Descrição conceitual: Representa os clientes da barbearia e armazena seus dados básicos. ================================================== 2. PROFISSIONAL ================================================== Atributos: ID_PROFISSIONAL — PK NM_PROFISSIONAL DS_ESPECIALIDADE CD_TELEFONE IN_ATIVO Descrição conceitual: Representa os profissionais responsáveis pela realização dos atendimentos. ================================================== 3. SERVICO ================================================== Atributos: ID_SERVICO — PK NM_SERVICO DS_SERVICO QT_DURACAO VL_PRECO IN_ATIVO Descrição conceitual: Representa os serviços oferecidos pela barbearia. ================================================== 4. AGENDAMENTO ================================================== Atributos: ID_AGENDAMENTO — PK ID_CLIENTE — FK ID_PROFISSIONAL — FK DT_AGENDAMENTO HR_INICIO HR_FIM TP_STATUS DS_OBSERVACAO IMPORTANTE: NÃO adicionar: - ID_AVALIACAO - ID_TABLE Esses atributos pertenciam à estrutura antiga e foram removidos/corrigidos no modelo final. Descrição conceitual: Representa o atendimento agendado e funciona como a principal entidade operacional do sistema. ================================================== 5. ITEM_AGENDAMENTO ================================================== Atributos: ID_AGENDAMENTO — PK/FK ID_SERVICO — PK/FK Essa entidade é uma entidade associativa. Os dois atributos juntos formam a identificação da associação. Ela existe para representar corretamente o relacionamento N:N entre AGENDAMENTO e SERVICO. ================================================== 6. PAGAMENTO ================================================== Atributos: ID_PAGAMENTO — PK ID_AGENDAMENTO — FK TP_FORMA_PAGAMENTO VL_PAGAMENTO TP_STATUS DT_PAGAMENTO Descrição conceitual: Representa o pagamento relacionado a um atendimento. ================================================== 7. AVALIACAO ================================================== Atributos: ID_AVALIACAO — PK ID_AGENDAMENTO — FK NR_NOTA DS_COMENTARIO DT_AVALIACAO Descrição conceitual: Representa a avaliação realizada pelo cliente sobre um atendimento. ================================================== RELACIONAMENTOS E CARDINALIDADES ================================================== As cardinalidades devem seguir EXATAMENTE o README. Utilizar a notação: (0,N) (1,1) (0,1) Não substituir por "1" e "∞". -------------------------------------------------- CLIENTE — AGENDAMENTO CLIENTE (0,N) — AGENDAMENTO (1,1) Interpretação: Um cliente pode possuir nenhum ou vários agendamentos. Cada agendamento pertence obrigatoriamente a um único cliente. -------------------------------------------------- PROFISSIONAL — AGENDAMENTO PROFISSIONAL (0,N) — AGENDAMENTO (1,1) Interpretação: Um profissional pode possuir nenhum ou vários agendamentos. Cada agendamento possui obrigatoriamente um profissional responsável. -------------------------------------------------- AGENDAMENTO — ITEM_AGENDAMENTO AGENDAMENTO (1,N) — ITEM_AGENDAMENTO (1,1) Interpretação: Um agendamento possui um ou vários itens de serviço. Cada item de agendamento pertence a um único agendamento. -------------------------------------------------- SERVICO — ITEM_AGENDAMENTO SERVICO (0,N) — ITEM_AGENDAMENTO (1,1) Interpretação: Um serviço pode ainda não ter sido utilizado em nenhum agendamento ou pode aparecer em vários agendamentos. Cada item de agendamento está relacionado a um único serviço. Esses dois relacionamentos representam: AGENDAMENTO N:N SERVICO por meio da entidade associativa: ITEM_AGENDAMENTO -------------------------------------------------- AGENDAMENTO — PAGAMENTO AGENDAMENTO (0,1) — PAGAMENTO (1,1) Interpretação: Um agendamento pode existir sem pagamento registrado ou possuir um pagamento. Cada pagamento obrigatoriamente pertence a um único agendamento. -------------------------------------------------- AGENDAMENTO — AVALIACAO AGENDAMENTO (0,1) — AVALIACAO (1,1) Interpretação: Um agendamento pode não possuir avaliação ou possuir uma avaliação. Cada avaliação obrigatoriamente pertence a um único agendamento. ================================================== ORGANIZAÇÃO VISUAL ================================================== O layout deve ser compacto, acadêmico e fácil de interpretar. Colocar: AGENDAMENTO no centro. CLIENTE à esquerda de AGENDAMENTO. PROFISSIONAL acima ou à direita de AGENDAMENTO. ITEM_AGENDAMENTO abaixo de AGENDAMENTO. SERVICO abaixo ou ao lado de ITEM_AGENDAMENTO. PAGAMENTO abaixo de AGENDAMENTO. AVALIACAO ao lado de PAGAMENTO ou abaixo de AGENDAMENTO. Uma organização recomendada é: CLIENTE (0,N) | | (1,1) | AGENDAMENTO / | \ / | \ / | \ / | \ / | \ / | \ / | \ PROFISSIONAL PAGAMENTO AVALIACAO (0,N) (0,1) (0,1) | | | (1,1) (1,1) (1,1) | (1,N) | ITEM_AGENDAMENTO | (1,1) | SERVICO (0,N) Organizar as linhas para evitar cruzamentos. ================================================== PADRÃO VISUAL ================================================== O DER deve ter aparência de um modelo acadêmico tradicional. Cada entidade deve ser representada por uma caixa retangular. Dentro de cada caixa: Primeira linha: NOME DA ENTIDADE Abaixo: lista de atributos. Exemplo: ┌──────────────────────────────┐ │ CLIENTE │ ├──────────────────────────────┤ │ PK ID_CLIENTE │ │ NM_CLIENTE │ │ CD_TELEFONE │ │ CD_EMAIL │ │ DT_CADASTRO │ └──────────────────────────────┘ As PK devem ser identificadas visualmente. As FK também devem ser identificadas visualmente. As entidades devem ser grandes o suficiente para que os nomes dos atributos possam ser lidos. As linhas entre as entidades devem ser contínuas. As cardinalidades devem aparecer próximas às extremidades das linhas. Não utilizar linhas pontilhadas. Não utilizar setas de fluxograma. Não utilizar símbolos de UML. Não utilizar uma grande área vazia com tabelas pequenas. Não transformar o DER em um modelo de tabelas SQL. ================================================== REGRA FUNDAMENTAL ================================================== O DER precisa representar fielmente o modelo conceitual descrito no README. A estrutura final deve ser: CLIENTE ↓ AGENDAMENTO ↓ ITEM_AGENDAMENTO ↓ SERVICO E também: AGENDAMENTO → PAGAMENTO AGENDAMENTO → AVALIACAO PROFISSIONAL → AGENDAMENTO As cardinalidades devem ser exatamente: CLIENTE (0,N) — AGENDAMENTO (1,1) PROFISSIONAL (0,N) — AGENDAMENTO (1,1) AGENDAMENTO (1,N) — ITEM_AGENDAMENTO (1,1) SERVICO (0,N) — ITEM_AGENDAMENTO (1,1) AGENDAMENTO (0,1) — PAGAMENTO (1,1) AGENDAMENTO (0,1) — AVALIACAO (1,1) Não alterar essas cardinalidades. Não adicionar entidades. Não remover entidades. Não adicionar atributos que não estejam na estrutura final. O resultado deve ser um DER acadêmico, limpo, legível e coerente com o README do projeto "Barbearia The Family Hair".
